## 一、网络排障场景分析

### 1.1 企业内网常见排障场景

基于企业网络运维实践，按 OSI 层级梳理常见排障场景：

| 场景分类 | 典型现象 | 发生频率 | 排查难度 |
|---------|---------|---------|---------|
| **物理层故障** | 网线/光模块异常、接口 Up/Down 抖动、CRC 错误暴增 | 中 | 低 |
| **二层故障** | VLAN 配置错误、STP 环路/广播风暴、MAC 漂移 | 高 | 中 |
| **三层故障** | 路由黑洞/单向可达、子网掩码不一致、网关不可达 | 高 | 中 |
| **安全策略拦截** | 防火墙 ACL 拒绝、NAT 未映射、IPS 误杀 | 高 | 高 |
| **传输层问题** | 端口不通、TCP 握手失败、MTU 不匹配 | 中 | 中 |
| **应用层故障** | DNS 解析失败、服务监听异常、资源耗尽 | 高 | 低 |
| **僵尸主机排查** | 内网主机被控、异常外联、C2 通信 | 中 | 高 |
| **网络性能劣化** | 丢包、延迟抖动、带宽拥塞 | 中 | 高 |

### 1.2 核心痛点

1. **排障工具分散**：ping/traceroute/telnet/DNS 查询等工具各自独立，缺乏统一入口，运维人员需在多个终端间切换
2. **故障定位慢**：缺乏端到端的连通性诊断链路，无法一键定位故障发生在哪一层、哪个节点
3. **防火墙策略"黑箱"**：深信服 AF 的安全策略命中情况难以直观查看，ACL 拦截导致的"网络不通"排查耗时最长
4. **僵尸主机发现滞后**：依赖人工巡检或安全设备告警，缺乏主动扫描+异常行为关联的能力
5. **排障经验难沉淀**：同类故障反复排查，缺乏排障记录和知识库机制
6. **设备与网络状态脱节**：设备台账是静态资产信息，缺乏实时网络可达性/性能状态关联

## 二、新功能提案

### P0 — 必须实现（核心排障能力，直接解决高频痛点）

---

#### 功能 1：网络连通性诊断工具箱

- **用户故事**：As a 网络运维人员, I want 在一个页面上执行 ping/traceroute/端口探测/DNS 解析等操作, so that 我不需要登录多台服务器或终端就能快速定位网络故障层级
- **核心功能点**：
  - ICMP Ping：支持单 IP 和网段批量 ping，显示丢包率/平均延迟
  - Traceroute：可视化路由跳数，标注每一跳的 IP、延迟、是否超时
  - TCP 端口探测：指定 IP+Port 进行连通性测试（替代 telnet/nc）
  - DNS 解析：指定域名查询解析结果，支持指定 DNS 服务器
  - 诊断报告：一键生成连通性诊断摘要（可达/不可达/部分可达 + 故障层级判断）
- **与现有模块关联**：
  - 设备台账 → 可从设备列表直接发起诊断
  - IP 存活扫描 → 诊断结果可补充扫描结果
  - 系统监控 → 诊断时可关联目标设备的监控数据
- **预期价值**：将排障工具从"多终端切换"整合为"单页操作"，预计单次排障时间缩短 40%+

---

#### 功能 2：防火墙策略查询与命中分析

- **用户故事**：As a 网络运维人员, I want 查询深信服 AF 的安全策略规则并查看命中计数, so that 我能快速判断网络不通是否因防火墙策略拦截导致
- **核心功能点**：
  - 策略查询：按源 IP/目的 IP/端口/协议 检索匹配的安全策略规则
  - 命中计数：展示策略命中次数和最近命中时间
  - 会话表查询：查指定 IP 的活跃会话/历史会话
  - NAT 规则查询：查看 NAT 映射关系，确认回包路径
  - 策略模拟：输入源/目的/端口，模拟匹配哪条策略（放行/拒绝）
- **与现有模块关联**：
  - 设备台账 → 防火墙作为设备类型管理
  - 攻击事件管理 → 安全策略与攻击事件关联分析
  - 网络连通性诊断 → 诊断"端口不通"时可联动查询防火墙策略
- **预期价值**：解决防火墙"黑箱"痛点，ACL 拦截类故障排查时间预计缩短 60%

---

#### 功能 3：Zabbix 告警集成与联动

- **用户故事**：As a 网络运维人员, I want 在运维平台中查看 Zabbix 告警并联动排障, so that 我不需要在 Zabbix 和运维系统之间来回切换
- **核心功能点**：
  - 告警聚合：通过 Zabbix API 拉取告警，按时间/严重级别/设备分组展示
  - 告警与设备关联：告警自动匹配设备台账中的设备信息
  - 一键排障联动：从告警直接跳转执行连通性诊断
  - 告警静默/确认：在运维平台操作告警状态，同步回 Zabbix
  - 告警统计报表：告警趋势、MTTR（平均修复时间）统计
- **与现有模块关联**：
  - 设备台账 → Zabbix host 与设备关联
  - 系统监控 → 互补：系统监控为 Agent 拉取，Zabbix 为被动采集
  - 首页概览 → 告警卡片
  - 中控大屏 → 告警数据可视化
- **预期价值**：实现告警发现→设备定位→故障诊断的闭环，减少跨系统操作

### P1 — 应该实现（增强排障效率，利用现有数据产生新价值）

---

#### 功能 4：僵尸主机排查助手

- **用户故事**：As a 网络运维人员, I want 系统帮我识别内网中可能被控的僵尸主机, so that 我能主动处置而不是等到安全设备告警
- **核心功能点**：
  - 异常外联检测：基于 IP 存活扫描数据 + 防火墙会话日志，标记与外网异常通信的内网主机
  - 行为特征匹配：检测频繁外联、非常规端口通信、C2 特征连接（如心跳间隔、特定域名）
  - 黑名单比对：内网 IP 与威胁情报黑名单（IP/域名）自动比对
  - 排查清单：生成疑似僵尸主机列表，含异常行为描述和证据链
  - 处置工单：一键创建桌面运维工单进行处置
- **与现有模块关联**：
  - IP 存活扫描 → 提供内网主机基线
  - 攻击事件管理 → 关联已知攻击事件
  - 安全事件中心 → CVE 和威胁情报数据源
  - 桌面运维工单 → 处置闭环
  - 防火墙策略查询 → 获取会话日志
- **预期价值**：从被动响应转为主动发现，预计僵尸主机发现时间从天级缩短至小时级

---

#### 功能 5：网络拓扑可视化

- **用户故事**：As a 网络运维人员, I want 看到网络拓扑图并标注故障节点, so that 我能直观定位故障影响范围
- **核心功能点**：
  - 拓扑自动发现：基于设备台账 + SNMP/LLDP 信息自动生成拓扑
  - 手动编辑：支持拖拽调整拓扑布局、添加连线和标注
  - 状态标注：节点颜色反映设备在线/离线/告警状态
  - 故障影响分析：选中故障节点，高亮受影响的下游链路和设备
  - 路径追踪：可视化展示源到目的的报文路径
- **与现有模块关联**：
  - 设备台账 → 拓扑节点数据源
  - Zabbix 告警集成 → 节点状态
  - 网络连通性诊断 → 路径追踪
  - 中控大屏 → 拓扑图展示
- **预期价值**：排障时直观定位故障位置和影响范围，降低排障认知负荷

---

#### 功能 6：排障工单与知识库

- **用户故事**：As a 网络运维人员, I want 记录排障过程和解决方案到知识库, so that 下次遇到同类故障可以快速参考
- **核心功能点**：
  - 排障记录：从诊断工具箱一键创建排障工单，自动填充诊断结果
  - 解决方案记录：记录故障原因、处理步骤、最终解决方案
  - 知识库：可搜索的排障案例库，按故障类型/设备/关键词检索
  - 智能推荐：基于当前诊断结果，推荐相似历史案例
  - 排障统计：常见故障类型、平均修复时间、人员效率统计
- **与现有模块关联**：
  - 桌面运维工单 → 复用工单流程
  - 网络连通性诊断 → 诊断结果自动填充
  - 周报月报 → 排障数据纳入报表
- **预期价值**：沉淀排障经验，避免同类故障重复排查，新人上手更快

### P2 — 锦上添花（提升体验，长期价值）

---

#### 功能 7：网络性能基线与异常检测

- **用户故事**：As a 网络运维人员, I want 系统自动学习网络性能基线并在异常时告警, so that 我能在用户投诉前发现网络劣化
- **核心功能点**：
  - 性能数据采集：基于 Zabbix/自研探针采集延迟、丢包率、带宽利用率
  - 基线自学习：自动计算各链路的性能基线（均值+波动范围）
  - 异常检测：偏离基线时自动告警
  - 趋势分析：性能趋势图，预测即将出现瓶颈的链路
  - 历史对比：对比当前与历史同期的性能数据
- **与现有模块关联**：
  - Zabbix 告警集成 → 性能数据源
  - 系统监控 → 服务器侧性能补充
  - 网络拓扑可视化 → 链路性能标注
- **预期价值**：从被动排障转为主动预防，减少用户感知到的网络故障

---

#### 功能 8：批量设备配置巡检

- **用户故事**：As a 网络运维人员, I want 定期自动检查关键设备配置是否符合安全基线, so that 我能提前发现配置漂移和安全隐患
- **核心功能点**：
  - 配置基线定义：定义关键配置项的安全基线（如 SNMP community、ACL 规则、SSH 版本）
  - 定时巡检：定期 SSH/Telnet 登录设备，采集配置并与基线比对
  - 漂移告警：检测到配置漂移时告警
  - 巡检报告：生成配置合规性报告
  - 一键修复：对不符合基线的配置项提供修复建议和回滚操作
- **与现有模块关联**：
  - 设备台账 → 设备列表和 SSH/Telnet 凭据
  - 配置变更管理 → 配置变更记录
  - 配置备份 → 配置快照
  - 安全事件中心 → 安全基线参考
- **预期价值**：主动发现配置风险，减少因配置错误导致的网络故障

## 四、实施建议

### 4.1 推荐开发路线

```
Phase 1（P0，6-8 周）：
  ├─ 网络连通性诊断工具箱  ← 独立性强，快速见效
  ├─ Zabbix 告警集成        ← 已在计划中，优先启动
  └─ 防火墙策略查询          ← 需深信服 AF API 对接，可并行

Phase 2（P1，8-12 周）：
  ├─ 排障工单与知识库        ← 工期短，复用工单模块
  ├─ 僵尸主机排查助手        ← 依赖 Phase 1 的诊断+防火墙数据
  └─ 网络拓扑可视化          ← 技术难度最高，可拆分迭代

Phase 3（P2，按需启动）：
  ├─ 网络性能基线与异常检测
  └─ 批量设备配置巡检
```

### 4.2 技术可行性关注点

1. **深信服 AF API 对接**：需确认 AF 版本是否开放 REST API，部分旧版本仅支持 CLI，需通过 SSH 解析输出
2. **Zabbix API 版本**：确认 Zabbix 版本（5.0/6.0/7.0），API 差异较大
3. **拓扑可视化技术选型**：Bootstrap + D3.js 或 Cytoscape.js，SQLite 存储拓扑关系数据需评估性能
4. **SSH 批量执行**：设备巡检和诊断功能需通过 Paramiko/Netmiko 执行远程命令，需管理并发和超时
5. **SQLite 性能边界**：性能基线数据量增长后需考虑数据归档策略

### 4.3 风险提示

- 深信服 AF API 可能需要额外授权或版本升级
- 网络拓扑自动发现依赖设备 SNMP/LLDP 配置，部分老旧设备可能不支持
- 僵尸主机排查的误报率需通过规则调优逐步降低，上线初期建议以"辅助参考"定位

## 五、总结

本次评估共提出 **8 项功能**，其中 P0 级 3 项、P1 级 3 项、P2 级 2 项。核心思路是：

1. **先补工具**（诊断工具箱）— 让运维人员有统一的排障入口
2. **再接数据**（Zabbix + 防火墙）— 打通数据孤岛，让告警和策略可查
3. **后建智能**（僵尸主机、拓扑、知识库）— 在数据基础上实现智能化排障

所有功能均基于 Flask + SQLite 内网架构设计，无云端依赖，可在企业内网独立部署运行。
